## 2. Таблица и модель данных

Схема двух таблиц в `solution.create_tables`:

```sql
CREATE TABLE IF NOT EXISTS user_actions (
    user_id    int,
    event_time timestamp,
    event_type text,        -- login | purchase | view
    payload    text,        -- детали события (JSON)
    PRIMARY KEY (user_id, event_time)
) WITH CLUSTERING ORDER BY (event_time DESC)
  AND COMPRESSION = {'class': 'org.apache.cassandra.io.compress.LZ4Compressor'};
```

`user_actions_none` — та же структура, но `COMPRESSION = {'enabled': 'false'}`
(в Cassandra 5.0 класс `NoCompressor` не регистрируется, отключение сжатия задаётся
`{'enabled': 'false'}`).

**Почему партиция по `user_id`.** Запись — действие конкретного пользователя, чтение —
его лента. Партиционный ключ `user_id` кладёт все события одного пользователя в одну
партицию, поэтому чтение ленты — это чтение одной партиции (одного узла-координатора),
а не сканирование. Запрос `WHERE user_id = ?` — эффективный точечный доступ без
secondary-индексов и без `ALLOW FILTERING`.

**Зачем обратный порядок кластеризации.** Внутри партиции строки упорядочены по
`event_time DESC` — самые свежие события лежат первыми. Тогда «лента последних N
событий» читается просто `LIMIT N` с начала партиции, и движок отдаёт первые N строк
без чтения и сортировки остальных. Это ровно паттерн «хвост журнала» с минимальной
стоимостью.

**Коллизия `event_time`.** `(user_id, event_time)` — это композитный первичный ключ,
где `event_time` — clustering key. Если два события одного пользователя придут
**с одинаковым `event_time`**, это одна и та же строка: вторая запись **перезапишет**
первую (last-write-wins по той же ячейке). Для аудита это риск — теряется событие
(например, два входа в одну и ту же секунду). Изменение схемы: сделать clustering key
уникальным — например `(user_id, event_time, event_id)` с `event_id` типа `timeuuid`
или `uuid` (или дополнить key номером/порядковым полем). Тогда каждое действие —
отдельная строка, и перезаписи нет, а порядок по-прежнему диктуется `event_time`.

Проверено сценарием `data`: partition key `user_id`, clustering `event_time DESC`,
колонки `event_type`/`payload`, сжатие LZ4 у `user_actions` и его отключение у
`user_actions_none`.

## 3. Вставка и чтение

`insert_events` вставляет `n` событий через **PreparedStatement**:

```sql
INSERT INTO user_actions (user_id, event_time, event_type, payload) VALUES (?, ?, ?, ?)
```

`read_last` читает ленту с `LIMIT ?`; порядок по убыванию уже задаёт кластеризация,
сортировать на клиенте не нужно:

```sql
SELECT user_id, event_time, event_type, payload FROM user_actions
WHERE user_id = ? LIMIT ?
```

Результат сценария `bulk` (`artifacts.bulk`, секунды):

| Что вставлено | Сколько | Время | Среднее на запись |
|---|---|---|---|
| События пользователя 1001 (`login`, `purchase`, `view`) | 10 000 | 5.887 с | ≈ 0.59 мс |

Проверки: ровно 10 000 строк в партиции 1001 (обе таблицы), чтение 5 последних в
порядке убывания времени.

**Что даёт PreparedStatement.**
1. **Компиляция один раз, выполнение много раз.** Запрос разбирается и готовится
   (query plan + bind-описания) на сервере однократно; при каждом `execute` передаются
   только параметры. Для 10 000 одинаковых по форме INSERT это огромная экономия на
   парсинге.
2. **Защита от инъекций.** Параметры биндятся по плейсхолдерам, значения никогда не
   интерполируются в строку запроса.
3. **Стабильная маршрутизация.** Cassandra вычисляет координатора по partition key из
   prepared-утверждения; драйвер также кэширует prepared-метаданные.
4. **Консистентность на утверждении.** В задании уровень задаётся на `bound.consistency_level`,
   а не на сессии — одна сессия обслуживает все четыре замера с разными уровнями.

## 4. Консистентность

Замеры сценария `consistency` (1000 записей, чтение 20 последних; медиана 5 прогонов
после прогрева, `artifacts.consistency`):

| Уровень | Запись, мс | Чтение, мс |
|---|---|---|
| ONE | 465 | 2 |
| QUORUM | 678 | 3 |

**Формула W + R > N.** N = 3 (число реплик, replication factor = 3). Если запись
подтверждается на **W** узлах, а чтение читается из **R** узлов (с пересечением для
согласования версий), то при W + R > N любые W и R множества **обязательно пересекаются**
хотя бы по одному узлу. Значит чтение увидит либо самую свежую версию, либо сможет её
восстановить — гарантируется **strong consistency** (строгое согласование). Классический
выбор: W = R = QUORUM (= 2 при N = 3), тогда 2 + 2 > 3.

- **ONE** — запись подтверждается на 1 узле, чтение идёт с 1 узла (1 + 1 = 2, не > 3).
  Гарантий актуальности нет: чтение может попасть на узел без последней версии.
- **QUORUM** — запись на 2 узла, чтение с 2 узлов. Согласование версий по меткам времени
  даёт актуальный результат; при недоступности узла операция может завершиться неудачей
  (нет кворума), но не вернуть устаревшие данные.

В замерах это видно: запись QUORUM медленнее (должна подтвердиться на двух узлах),
чтение почти одинаковое (данные уже сходились и второй узел на 20 строк почти ничего
не добавляет).

**Какой уровень выбрал бы для ленты событий.** Для аудита корректность важнее латентности,
поэтому запись — на **QUORUM** (не теряем события, переживает недоступность одной реплики).
Чтение ленты можно делать на **LOCAL_QUORUM/QUORUM**, но для свежих событий допустимо
**ONE**: если редкое событие запоздает на чтение, следующее чтение его увидит, а цена
(одна реплика вместо двух) ниже. Главное — не снижать консистентность **записи**.

## 5. Сжатие

Данные `results/tablestats.txt` (LZ4) и `results/tablestats_plain.txt` (без сжатия),
сняты после `nodetool flush hw3` по наполненным таблицам (10 000 строк):

| Таблица | Space used (total), B | SSTable count | SSTable Compression Ratio |
|---|---|---|---|
| `user_actions` (LZ4) | 151 609 | 1 | 0.38191 |
| `user_actions_none` (без сжатия) | 386 886 | 1 | −1.00000 |

LZ4 сжал данные примерно в 2.55 раза (386 886 → 151 609 Б, ratio 0.38). Для таблицы без
сжатия ratio равен −1 (метрика не применима).

**Компромисс сжатия.** Выигрыш — **место и I/O**: данные меньше, в disk-кэш и на диск
уходит меньше байт, дешевле репликация и бэкапы. Цена — **CPU**: на записи данные
сжимаются, на чтении распаковываются по сжатым блокам. Также запись/чтение получают
небольшой накладной расход на блокировку блока. Для этого кейса сжатие выгодно: журнал —
текстовые payload (JSON), хорошо сжимаются; события почти не перезаписываются (append-only),
а чтение ленты распаковывает лишь несколько блоков. LZ4 выбран как компромисс
скорость/степень сжатия — дешёвое CPU, приличное сжатие.

## 6. Bloom-фильтр

Для `hw3.user_actions` (`tablestats.txt`):

| Показатель | Значение |
|---|---|
| Bloom filter false positives | 0 |
| Bloom filter false ratio | 0.00000 |

**Что делает bloom-фильтр.** На каждый SSTable строится битовый фильтр по partition keys,
которые в нём есть. Перед disk lookup фильтр отвечает: **«ключа точно нет»** или «возможно
есть». Если фильтр говорит «нет» — Cassandra пропускает этот SSTable, **не выполняя disk
lookup**: это экономия чтения, ведь на попадание надо искать по индексу и читать блок.
Bloom-фильтр не даёт ложноотрицательных ответов (ключ, которого нет, никогда не «нашёлся»),
поэтому данные не теряются.

**О чём метрика и когда полезна.** `false positives` — число ключей, которые фильтр
«принял» за присутствующие, но которых в SSTable нет (пришлось лишний раз лезть на диск);
`false ratio` — доля таких обращений. Ненулевой ratio означает лишние disk lookups.
Фильтр особенно полезен, когда **ключ часто отсутствует** (нет записи), а таблиц/SSTable
много — он отсекает большинство ненужных обращений. Он неважен, когда почти все обращения
попадают в существующие ключи (тогда всё равно читаем) или когда данных и SSTable мало
(весь файл в кэше). В нашем прогоне false ratio = 0 — фильтр сработал идеально.

## 7. Repair

`results/repair.txt` — `nodetool repair hw3`:

```
Starting repair command #2 ... repairing keyspace hw3
  (parallelism: parallel, incremental: true, # of ranges: 48, ...)
Repair completed successfully  ... finished in 0 seconds
```

**Anti-entropy и зачем repair.** При ненормальном завершении или сбое узла реплики могут
разойтись: данные записаны только на часть узлов. **Anti-entropy repair** активно сверяет
и **исправляет расхождения между репликами вне пути чтения** — узлы по ranges сравнивают
свои данные по контрольным суммам и доводят отстающие реплики. Это фоновое
профилактическое согласование, которое не зависит от того, читал ли кто-то эти ключи.

**Когда без repair не обойтись.** Repair обязателен при регулярных сбоях, долгих простоях
узла, операциях деления данных (resize/смена replication factor), а также для поддержания
гигиены при TTL. **При долгой работе без repair** реплики расходятся всё сильнее: чтение
может вернуть неактуальные (старые) данные; tombstones, отмечающие удаления/истечение
TTL, **не подчищаются** до истечения `gc_grace_seconds`, а если узел, где лежит tombstone,
долго недоступен — возможен и «возврат» удалённых данных. В итоге растут и расхождения,
и место.

**Repair vs read repair vs hinted handoff.**
- **Read repair** чинит **только те ключи, которых коснулось чтение**: при расхождении
  версий во время чтения более свежая запись разъезжается на отстающие реплики. Пассивно,
  в горячем пути.
- **Hinted handoff** компенсирует **короткие простои** узла: координатор хранит «хинт»
  (запись, которую не принял недоступный узел) и доставляет её, когда узел вернётся.
  Актуально только для записей в период простоя.
- **Repair** — это **активная, полная сверка всех данных** (по ranges) вне пути чтения;
  единственный способ гарантированно устранить расхождения, включая те, что hint/repaired
  не покрыли, и поддерживать согласованность кластера в целом.

## 8. TTL и компакция

`configure_twcs_ttl` для `user_actions`:

```sql
ALTER TABLE user_actions WITH
  compaction = {'class': 'TimeWindowCompactionStrategy',
                'compaction_window_unit': 'DAYS', 'compaction_window_size': 1}
  AND default_time_to_live = 2592000;   -- 30 дней
```

Проверено сценарием `compaction`: класс TWCS, окно 1 день, TTL 30 дней; TTL-эксперимент —
5 строк с TTL 5 с: **до истечения 5, после истечения 0**.

`results/compaction.txt` — принудительная компакция `user_actions` (major compaction,
bytes 146 047 → 146 047) и история компакций.

**Почему TWCS, а не STCS.** Журнал событий — строго **append-only** по времени: новые
строки попадают в текущий временной отрезок, старые только удаляются TTL. **TWCS** группирует
SSTable по временным окнам (здесь — по дням) и компактирует **только внутри окна**; окно
закрывается и остаётся одним SSTable, который больше не трогается до истечения TTL.
Это даёт предсказуемые, дешёвые компакции и идеальную утилизацию TTL (целые устаревшие
SSTable удаляются без «перетасовки» данных). **STCS** наоборот сливает SSTable по размеру —
при постоянно растущем журнале она постоянно перекомпактирует огромные таблицы (write
amplification), многократно переписывая одни и те же данные, — для журнала это расточительно.

**TTL и `gc_grace_seconds`.** TTL помечает строку tombstone'ом; физически она удаляется
при компакции. По умолчанию Cassandra хранит tombstone не меньше `gc_grace_seconds`
(по умолчанию 10 дней / 864000 с), чтобы успеть разослать удаление на все реплики и не
«воскресить» удалённые строки. Пока tombstone живёт, его нельзя компактить раньше этого
срока. Поэтому для TTL 30 дней важно, чтобы `gc_grace_seconds` был **меньше** TTL: тогда
строки успевают истечь и tombstones доехать до всех реплик, и лишь затем подчищаются.
Если `gc_grace_seconds` ≥ TTL, потенциально возможен возврат данных после истечения TTL.

**Почему TTL предпочтительнее массового DELETE.** TTL — декларативный «самоистекающий»
механизм: строка удаляется по времени без отдельных операций, не требует координации
«когда именно удалить», не нагружает кластер тысячами DELETE и не рискует «пропустить»
часть строк. DELETE вручную требует фоновых заданий, оставляет те же tombstones, но
полагается на то, что кто-то выполнит удаление вовремя и по правильному ключу. Для
журнала с известным сроком хранения TTL — правильный выбор: задал один раз в схеме,
и строки исчезают сами, а TWCS эффективно удаляет целые устаревшие SSTable.
