### 1.3 Объяснение

1. **Смысл процента на примере.** Для RU за 20–26 октября `events_total = 2 771 858`, `events_under_20 = 653 114`. Доля `100 × 653114 / 2771858 = 23.56 %` означает: из каждых 100 завершённых прослушиваний, зафиксированных для России за этот период, примерно 23.56 завершились с длительностью менее 20 секунд (то есть почти четверть прослушиваний обрываются почти сразу — до 20-й секунды).

2. **Доля событий ≠ доле слушателей.** Доля событий считает **события** (знаменатель — число прослушиваний), а доля слушателей считала бы **уникальных пользователей**. На строках KZ из примера: у единственного пользователя `201` два события — одно `5 c` (< 20) и одно `20 c` (не < 20). Доля событий короче 20 сек = 1 из 2 = 50 %. При этом доля слушателей, у которых было хотя бы одно такое прослушивание, = 1 из 1 = 100 % (у пользователя 201 такое событие есть). Разные знаменатели: события против уникальных слушателей.

## 3. Кодеки и порядок значений

### 3.1 Подготовка, контроль данных и частей

```sql
CREATE TABLE takt.hw_codec_ordered (event_no UInt64,
    t_zstd DateTime('UTC') CODEC(ZSTD(1)),
    t_delta DateTime('UTC') CODEC(Delta, ZSTD(1)),
    t_double_delta DateTime('UTC') CODEC(DoubleDelta, ZSTD(1)))
ENGINE = MergeTree ORDER BY event_no
SETTINGS index_granularity = 8192, index_granularity_bytes = 0,
         min_bytes_for_wide_part = 0, min_rows_for_wide_part = 0;

CREATE TABLE takt.hw_codec_mixed AS takt.hw_codec_ordered
ENGINE = MergeTree ORDER BY (cityHash64(event_no), event_no)
SETTINGS index_granularity = 8192, index_granularity_bytes = 0,
         min_bytes_for_wide_part = 0, min_rows_for_wide_part = 0;

INSERT INTO takt.hw_codec_ordered
SELECT number, toDateTime('2026-10-20 00:00:00','UTC') + toIntervalSecond(number) AS event_time,
       event_time, event_time
FROM numbers(500000);
INSERT INTO takt.hw_codec_mixed SELECT * FROM takt.hw_codec_ordered;
OPTIMIZE TABLE takt.hw_codec_ordered FINAL;
OPTIMIZE TABLE takt.hw_codec_mixed FINAL;
```

Контроль данных (для каждой таблицы): `rows_count = 500000`, `unique_ids = 500000`, `first_id = 0`, `last_id = 499999`, `bad_rows = 0`.

Контроль частей (`system.parts`): две строки — по **1 активной Wide-части** и **500 000** строк в каждой таблице.

### 3.3 Измерение размеров колонок

```sql
SELECT table, column,
       sum(column_data_uncompressed_bytes) AS uncompressed_bytes,
       sum(column_data_compressed_bytes) AS compressed_bytes,
       round(sum(column_data_uncompressed_bytes) / nullIf(sum(column_data_compressed_bytes),0), 2) AS compression_ratio
FROM system.parts_columns
WHERE database='takt' AND active
  AND table IN ('hw_codec_ordered','hw_codec_mixed')
  AND column IN ('t_zstd','t_delta','t_double_delta')
GROUP BY table, column ORDER BY table, column;
```

|---|---|---|---|---:|

| hw_codec_ordered | t_double_delta | 2000000 | 2325 | 860.22 |

### 3.4 Объяснение

1. **Сравнение цепочек внутри порядка.** В **регулярной** таблице минимальный сжатый размер у `t_delta` (2 234 Б), почти так же у `t_double_delta` (2 325 Б), а `t_zstd` намного больше (1 332 284 Б). В **перемешанной** таблице минимальный у `t_zstd` (1 543 831 Б), затем `t_delta` (1 586 160 Б) и `t_double_delta` (1 962 850 Б).

2. **Одна цепочка в двух порядках.** `t_delta`: в регулярной таблице 2 234 Б, в перемешанной 1 586 160 Б (~710× больше). Причина — разностное кодирование и соседство значений. Delta хранит разность с предыдущим значением. В регулярном порядке соседние метки отличаются ровно на 1 секунду, дельты крошечные и почти постоянные → почти нулевой объём. В перемешанном порядке соседние значения — случайные метки с разностями в десятки/сотни тысяч секунд (185142, −40428, …), большие и нерегулярные → выигрыша нет, объём сравним с исходными 4-байтовыми значениями.

3. **Delta vs DoubleDelta и роль ZSTD.** `Delta` кодирует разность с предыдущим значением; `DoubleDelta` — разность разностей (вторую производную), что хорошо для последовательностей с постоянным шагом/трендом. `ZSTD` — универсальное энтропийное сжатие, которое ужимает оставшуюся избыточность независимо от конкретного преобразования. Дополнительные преобразования **не гарантируют** меньший результат: они без потерь, но помогают только если полученные числа становятся меньше/регулярнее. На случайных данных разности столь же велики и нерегулярны, как исходные значения, поэтому преобразование ничего не даёт (а DoubleDelta может даже ухудшить), а ZSTD всё равно работает с высокой энтропией. Отсюда в перемешанной таблице `t_zstd` даже меньше, чем `t_delta`/`t_double_delta`.

4. **Почему порядок хранения нельзя выбирать только по сжатию.** Ключ сортировки определяет и сжатие, и **чтение**. Ключ, оптимальный для сжатия (упорядочивание по тесно связанной колонке), может быть плох для фактических фильтров и вызывать многократно больший объём чтения. В задании 2 разные ключи давали разный объём чтения для разных запросов (Германия: 8 гранул против 102; Все страны: 114 против 102). Поэтому порядок хранения реальной таблицы выбирается с учётом нагрузки запросов, а не только по минимальному размеру.

**Сохранение информации.** Исходные времена событий хранятся цепочкой `Delta`/`DoubleDelta`+`ZSTD` — это **сжатие без потерь**: декомпрессия всегда восстанавливает точные исходные метки. Поэтому события за произвольный интервал (например, с 10:15 до 10:45 конкретного дня) можно посчитать **точно**. Если же вместо времён событий хранить только количества за день, произвольный подневной интервал посчитать точно уже нельзя — доступны только агрегаты по дням, и гранулярность ниже требуемой.

- `takt.hw_mv_events` (источник) — после загрузки истории `count() = 10 000 000` (N).
- `takt.hw_country_hourly` (target) — `SummingMergeTree((events, events_under_20, total_seconds)) ORDER BY (hour, country)`.
- MV создано без `POPULATE`; сразу после создания `SELECT count() FROM takt.hw_country_hourly` → **0** (инкрементальное MV не обработало ранее загруженную историю).

```sql
CREATE MATERIALIZED VIEW takt.hw_country_hourly_mv
TO takt.hw_country_hourly
AS
SELECT
    toStartOfHour(ended_at)      AS hour,
    country,
    count()                      AS events,
    countIf(played_seconds < 20) AS events_under_20,
    sum(played_seconds)          AS total_seconds
FROM takt.hw_mv_events
GROUP BY hour, country;
```

Затем история один раз записана напрямую в target `INSERT ... SELECT ... GROUP BY hour, country`.

### 4.5 Ответы на вопросы шага 6

1. **Что обработало MV при порции Б и почему изменился старый час.** MV инкрементально обрабатывает **новые вставки** в источник, а не всю историю. Порция Б — 3 новые строки: `19:00 RU 1`, `20:00 RU 10` — попадают в новые часы 27.10, а `24.10 12:34 RU 7` имеет `ended_at` из старого периода (24.10). MV не фильтрует по времени (`ended_at` любой), поэтому для этого события час `toStartOfHour` = 2026-10-24 12:00, и оно попало в уже существовавшую группу «RU, 24.10 12:00», увеличив её итоги на +1/+1/+7. Отдельное заполнение истории понадобилось потому, что инкрементальное MV создаётся «с нуля»: строки, загруженные **до** создания MV, оно не видит, поэтому история была агрегирована и записана в target вручную один раз.

2. **Зачем sum и GROUP BY при чтении target.** `SummingMergeTree` суммирует строки только **при фоновом слиянии** частей. До слияния одни и те же ключи `(hour, country)` могут лежать в нескольких частях несколькими строками (каждая вставка/MV-блок создаёт свою часть). Результат отчёта не должен зависеть от того, когда произошло слияние, поэтому при чтении итоги по группе объединяются вручную через `GROUP BY` + `sum(...)`.

3. **Правильная итоговая доля и средняя против «среднего из средних» для RU, 27.10 19:00.** В этой группе после Б: события = 5, коротких = 3, сумма секунд = 85.
   - Правильно: доля = 100 × 3 / 5 = **60.00 %**; средняя = 85 / 5 = **17.00 с**.
   - Усреднение долей двух порций: порция А дала бы долю 2/4 = 50 %, порция Б добавила одно короткое событие в эту группу → её «доля» 1/1 = 100 %. Среднее арифметическое (50 + 100) / 2 = **75 %** — неверно. Аналогично по средним: порция А 84/4 = 21 с, порция Б 1/1 = 1 с (добавлено одно событие длительностью 1 с) → среднее (21 + 1)/2 = **11 с**, тогда как правильная средняя 17 с. Ошибка в том, что у порций разные объёмы: усреднение процентов/средних игнорирует число событий в каждой порции, а правильная агрегация делит **сумму** на **сумму** по всем событиям группы.

4. **Можно ли пересчитать долю с порогом < 10, имея только target?** Нет, гарантированно нельзя. В target хранятся только `events`, `events_under_20` (для порога 20) и `total_seconds` — это агрегаты без распределения длительностей. Для порога 10 нужно, какие из событий длились < 10 с, а это отдельные значения `played_seconds`, которых в target нет. Без исходных событий и без известных контрольных длительностей долю «< 10 с» по произвольной истории из сохранённых данных получить нельзя (можно лишь примерно оценить, если знать долю < 20 и среднюю, но точного пересчёта не даёт).
